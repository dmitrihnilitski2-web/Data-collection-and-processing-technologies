# Варіант 2. Агент керування батареєю (BESS)

## 1. Джерела даних
Для навчання та тестування агента використовуються **синтетичні дані**, які генеруються середовищем (Environment). 
- **Тарифи на електроенергію:** 3 рівні:
  - Нічний (Cheap): 23:00 - 07:00 (1.0 ₴)
  - Денний (Mid): 07:00 - 17:00, 22:00 - 23:00 (2.5 ₴)
  - Піковий (Peak): 17:00 - 22:00 (5.0 ₴)
- **State of Charge (SOC):** Поточний рівень заряду батареї (від 0 до 10 кВт).
- **Час (Hour):** Поточна година доби (0-23).

## 2. Pipeline обробки даних
Оскільки дані генеруються в реальному часі під час симуляції, pipeline виглядає наступним чином:
1. **Генерація стану (State):** Збір інформації про поточну годину, розрахунок дискретного рівня тарифу та заокруглення SOC до цілого значення.
2. **Формування кортежу:** Стан конвертується у формат `(hour, tariff_level, soc_discrete)` для передачі в агента.
3. **Обчислення винагороди (Reward Shaping):** Після кожної дії система оцінює логічність дії: штрафує за заряд у пікові години та розряд у дешеві, і винагороджує за арбітраж (заряд вночі, розряд під час піку).
4. **Оновлення середовища:** Час зміщується на 1 годину, рівень заряду (SOC) оновлюється відповідно до обраної дії.

## 3. Модель/алгоритм
Використовується алгоритм навчання з підкріпленням **Q-Learning**.
- **Тип:** Tabular Q-Learning (на основі Q-таблиці), що підходить для дискретних просторів станів.
- **Параметри навчання:** 
  - `alpha` (швидкість навчання) = 0.1
  - `gamma` (дисконтування майбутніх винагород) = 0.99 (високий рівень критично важливий для довгострокового планування арбітражу).
  - `epsilon` (ймовірність дослідження) зменшується з 1.0 до 0.01 із кроком `epsilon_decay = 0.998`.

## 4. Агентна логіка (policy / decision-making)
Агент (Decision Maker) приймає рішення на основі поточної Q-таблиці (Policy).
Можливі дії (Actions):
- `0`: Hold (Нічого не робити)
- `1`: Charge (Зарядити на 2.0 кВт)
- `2`: Discharge (Розрядити на 2.0 кВт)

Під час навчання агент використовує **Epsilon-Greedy Policy** для балансу між дослідженням нових стратегій (Exploration) і використанням набутих знань (Exploitation). Після завершення навчання (наприклад, після 2000 епізодів) агент переходить у режим **Exploitation**, обираючи лише дії з найвищим Q-value для поточного стану.

## 5. Інтерфейс (API / UI / CLI)
Проєкт реалізовано у вигляді **Full-stack застосунку**:
- **Backend (API):** Написаний на Python з використанням фреймворку **FastAPI**. 
  - `POST /api/train` — запуск навчання агента.
  - `GET /api/step` — отримання рішення від агента для наступної години та оновлення стану середовища.
- **Frontend (UI):** Веб-інтерфейс (HTML/CSS/JS), що візуалізує рівень заряду батареї (у вигляді графічної батареї), поточний тариф (кольорові індикатори) та обрану агентом дію. 
- **CLI:** Навчання та тестування алгоритму можна запускати безпосередньо через консоль файлом `agent.py`.

## 6. Метрики якості
Оскільки це алгоритм навчання з підкріпленням, стандартні метрики класифікації (accuracy, F1) тут не застосовуються. Використовуються специфічні RL-метрики:
- **Total Episodic Reward (Сумарна винагорода):** Основна метрика. Успішно навчений агент повинен показувати стабільно високу винагороду в кінці епізоду.
- **Convergence Rate (Швидкість збіжності):** Кількість епізодів, необхідних для досягнення стабільної (максимальної) сумарної винагороди (у нашому випадку ~1000-2000 епізодів).
- **Financial Savings / Arbitrage Profit (Економічний ефект):** Сумарна економія або прибуток від арбітражу за цикл (день/тиждень) у гривнях.
- **Latency (Затримка прийняття рішень):** Час пошуку оптимального рішення в Q-таблиці під час інференсу (складає менше 1 мілісекунди, O(1)).
